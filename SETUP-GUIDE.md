# Setup guide: portfolio on AWS Amplify, from nothing to live

This is the full walkthrough of how this portfolio was set up on 27 October 2026 for the AWS Student Builder Challenge. It is written so that anyone can follow it by hand with no prior AWS experience. Where a step was done for me by an AI assistant, the manual version is described instead, because the result is the same.

Time for the whole guide: about three hours, including waiting for emails.

What you will have at the end:

- A personal AWS account that is secured and will warn you about spending
- A GitHub repository holding the site
- A static website hosted on AWS Amplify, live on an HTTPS address, redeploying itself every time you push

---

## Part 1: Create and secure a personal AWS account

### 1.1 Register

1. Go to https://signin.aws.amazon.com/signup?request_type=register
2. Enter a personal email address. Keep this account separate from any business account you run.
3. Account name: something like `Your Name Personal`.
4. Confirm the email with the code AWS sends.
5. Create a strong root password and save it in a password manager. This is the "root user" password; you will use it rarely.
6. Choose **Personal** use, fill in your own name, address and phone number.
7. Enter a payment card. AWS asks for this even on the free tier. It will not be charged unless you use paid services.
8. Complete the phone or SMS verification.
9. Choose the **Basic support** plan (free).
10. Wait for the "Your account is ready" email, usually within a few minutes.

### 1.2 Set your Region

1. Sign in at https://console.aws.amazon.com as the **Root user**.
2. In the top-right Region menu, choose **Europe (London) eu-west-2** (or the Region nearest you). This only sets where new resources are created.

### 1.3 Turn on multi-factor authentication for the root user

Root can do anything in the account, so it needs a second factor.

1. Click your account name at the top right, then **Security credentials**.
2. Under **Multi-factor authentication (MFA)**, click **Assign MFA device**.
3. Device name: `root-authenticator`. Choose **Authenticator app**.
4. Scan the QR code with an authenticator app (Google Authenticator, Microsoft Authenticator, Authy, 1Password).
5. Enter two consecutive codes from the app and click **Add MFA**.
6. Do **not** create root access keys. Leave that section empty.

### 1.4 Create an everyday admin user

AWS's advice is to stop using root after setup. You create a second identity with admin rights and MFA, and use that for all daily work.

1. Go to https://console.aws.amazon.com/iam/home#/users and click **Create user**.
2. User name: `yourname-admin` (this project used `gibson-admin`).
3. Tick **Provide user access to the AWS Management Console**. Choose **I want to create an IAM user**.
4. Leave **Autogenerated password** and **Users must create a new password at next sign-in** selected. Click **Next**.
5. Permissions: choose **Attach policies directly**, search `AdministratorAccess`, tick it, click **Next**, then **Create user**.
6. On the "Retrieve password" screen, click **Show** and save the temporary password in your password manager, or download the CSV. This is the only time it is shown.
7. Note the **Console sign-in URL**: `https://<your-account-id>.signin.aws.amazon.com/console`. Bookmark it.
8. Click **Return to users list**, open the new user, go to the **Security credentials** tab, click **Assign MFA device**, and repeat the authenticator steps with a second entry in your app.
9. Sign out of root. Sign in at the bookmarked URL as the new user. AWS forces you to set a new password immediately.

From now on, root is for billing emergencies only.

### 1.5 Set a budget alert

A budget is an **alert**, not a spending cap. AWS still bills past it; the alert means you find out within a day instead of at month end.

1. Go to https://us-east-1.console.aws.amazon.com/costmanagement/home#/budgets/create
2. Choose **Customize (advanced)**, then **Cost budget**, click **Next**.
3. Name: `Personal-Learning-Budget`. Period: **Monthly**. Renewal: **Recurring**. Method: **Fixed**.
4. Amount: budgets are in US dollars; `13` is about £10. Click **Next**.
5. Click **Add an alert threshold**: threshold `80`, trigger **Actual**, your email address.
6. Click **Add alert threshold** again: threshold `100`, trigger **Forecasted**, same email.
7. Click **Next** (skip the optional "actions" step), **Next**, review, then **Create budget**.
8. You will get a confirmation email from AWS Budgets. Nothing to click.

The first two monthly budgets on an account are free.

## Part 2: Create the GitHub repository

### 2.1 Create the repo

1. Sign in to GitHub and go to https://github.com/new
2. Name: `yourname-portfolio`. Visibility: **Public** (the hackathon needs a public repo link).
3. Tick **Add a README file**. Click **Create repository**.

### 2.2 Add the starter files

Create these in the repo (edit on GitHub or locally):

- `README.md`: what the site is, the stack, how to run it locally, the live URL once you have one.
- `BUILD-LOG.md`: three lines a day (did, broke, learned). This becomes your write-up.
- `CREDITS.md`: a table of every third-party asset, its source URL and licence.
- `LICENSE`: MIT for the code, with a note that your content and media are excluded.
- `.gitignore`: ignore `raw-audio/`, `scratch/`, `node_modules/`, `.env`, editor folders.
- `.gitattributes` containing `* text=auto eol=lf` so Windows and Linux agree on line endings.
- `js/channels.js`: the data model for the creative feature (stories, colours, file paths).
- `assets/audio/.gitkeep` and `assets/img/` folders.

### 2.3 Clone it to your computer

Install Git from https://git-scm.com if you do not have it. Then in PowerShell:

```powershell
cd C:\Users\<you>
git clone https://github.com/<you>/<repo>.git
cd <repo>
git config user.name "Your Name"
git config user.email "<id>+<you>@users.noreply.github.com"
git config core.autocrlf false
```

The no-reply email is under GitHub Settings, Emails. It keeps your real address out of the public history.

Test that you can push:

```powershell
Add-Content BUILD-LOG.md "`nSetup note: cloned and verified push access."
git add BUILD-LOG.md
git commit -m "Confirm local setup"
git push
```

The first push opens a browser window for GitHub sign-in. After that, credentials are cached.

**The mistake everyone makes once:** Git commands only work inside the repo folder. If you see `fatal: not a git repository`, you are in the wrong folder. Run `cd` into the repo first.

## Part 3: Gather assets

### 3.1 Headshot

Any clear photo of you, face lit from the front, plain background. Crop to a square, at least 1200 px, save as JPG under 150 KB. Put it in `assets/img/`. On this site, `gibson.jpg` (1200 px) is the hero and `gibson-600.jpg` is the social preview image.

### 3.2 Audio for the creative feature

The mixing desk needs one short loop per channel. Rules that matter when the files live in a public repo:

- A public GitHub repo **redistributes** the files, so the licence must allow that.
- **Freesound, Creative Commons 0** allows it. Filter the search to CC0, then check the licence line on each sound's own page before downloading.
- **Pixabay** forbids redistributing files as standalone content. Not suitable for a public repo.
- **BBC Sound Effects** is personal, educational and research use only, no redistribution. Not suitable.

Steps:

1. Create a free Freesound account; downloads require login.
2. Search with the licence filter: `https://freesound.org/search/?q=<terms>&f=license:"Creative Commons 0"`.
3. Open each sound's page, confirm it says **Creative Commons 0**, click **Download**. Note: Chrome may save audio to your Music folder rather than Downloads.
4. Move the originals into `raw-audio/` in the repo (ignored by Git, so the 30 MB WAVs never get pushed).
5. Record each file in `CREDITS.md`: title, creator, asset URL, licence.

### 3.3 Make the loops

With ffmpeg (https://ffmpeg.org, or `winget install ffmpeg`), for each file:

```bash
ffmpeg -ss 10 -t 20 -i raw-audio/original.wav -ac 1 \
  -af "loudnorm=I=-18:TP=-2:LRA=11,afade=t=in:st=0:d=0.2,afade=t=out:st=19.8:d=0.2" \
  -ar 44100 -c:a libmp3lame -b:a 128k assets/audio/channel.mp3
```

That takes 20 seconds starting at 0:10, makes it mono, normalises loudness, fades the ends so the loop does not click, and writes a 128 kbps MP3 of about 310 KB. If a source is already a designed loop, keep its full length so the loop point survives. Check the level afterwards:

```bash
ffmpeg -i assets/audio/channel.mp3 -af volumedetect -f null -
```

Aim for a mean around -18 dB and a peak below -1 dB. Then listen to every file. Six loops came to 2 MB in total.

## Part 4: Build the site

Plain HTML, CSS and JavaScript, no framework and no build step. That keeps Amplify's configuration trivial and makes every bug yours to read.

Files:

```
index.html          three core sections, sticky nav with the creative-feature hint
css/styles.css      layout, type, responsive rules
css/desk.css        the mixing desk section
js/main.js          nav highlighting and the text fallback for the stories
js/channels.js      data model: one object per channel
assets/img/         headshot, favicon
assets/audio/       the loops
```

Points that scored in the hackathon rubric:

- **Three core sections** reachable from a nav that stays on screen: About, Superpowers, Projects.
- **A visible hint** for the creative feature: the "Hear my story" item in the nav is always visible, never behind a hover.
- **A text fallback** so the stories are readable without the feature working (screen readers, broken audio).
- **Responsive** down to 390 px: tested by resizing the browser before deploying.
- Scripts use `type="module"`, which browsers block from `file://`. To preview locally, run `python -m http.server 8000` in the repo and open http://localhost:8000.

Commit and push:

```powershell
git add index.html css js assets CREDITS.md BUILD-LOG.md README.md
git commit -m "Add site"
git push
```

## Part 5: Deploy with AWS Amplify Hosting

### 5.1 Connect Amplify to GitHub

1. Sign in to AWS as your admin user. Make sure the Region at the top right is the one you chose in 1.2.
2. Go to https://console.aws.amazon.com/amplify/ and click **Create new app** (or **Deploy an app**).
3. Source code provider: **GitHub**. Click **Next**.
4. A GitHub window opens asking to install the **AWS Amplify** app on your account. If it does not appear, Chrome has blocked the popup: click the blocked-popup icon at the right of the address bar, allow popups for `console.aws.amazon.com`, then click **Update GitHub permissions** on the Amplify page.
5. In the GitHub window, choose **Only select repositories**, pick your portfolio repo, and click **Install & Authorize**. GitHub may ask for your password or 2FA code.
6. Back in Amplify, click the refresh icon next to the repository box. Select your repo. The branch `main` is selected automatically if it is the only one. Click **Next**.

### 5.2 App settings

1. App name: same as the repo.
2. Build settings are auto-detected. For a plain static site there is **no build command** and the output directory is `/`. Click **Edit YML file** to see what Amplify will do:

```yaml
version: 1
frontend:
  phases:
    build:
      commands: []
  artifacts:
    baseDirectory: /
    files:
      - '**/*'
  cache:
    paths: []
```

   Leave it as it is. Click **Next**.
3. Review, then **Save and deploy**.

### 5.3 Watch the first deployment

The app overview page shows the `main` branch as **Deploying**, then **Deployed**, usually within two minutes for a static site. The domain is `https://main.<app-id>.amplifyapp.com`.

Under the surface, Amplify stores the files in Amazon S3 and serves them through Amazon CloudFront, so your site is on a global content delivery network with HTTPS, with no extra setup.

### 5.4 Verify the live site

Open the URL in a private window (so no login or cache helps it):

- The page loads over HTTPS.
- Open the browser developer tools (F12), Console tab: no red errors. Network tab, reload: every file returns 200.
- Resize the window to phone width. The nav should still show the hint and the sections should stack.
- Click every link in the nav and the footer.

### 5.5 Prove continuous deployment

Edit `README.md` to add the live URL, commit and push. Watch the Amplify overview: within a minute it shows a new deployment with your commit message. Every push to `main` now redeploys the site. Screenshot that; it is the clearest evidence of a working pipeline.

## What was learned on day one

- Root is for emergencies; an admin user with MFA is for work.
- A budget alert tells you about overspend, it does not prevent it.
- "Free to download" and "free to redistribute" are different questions, and a public repo is redistribution.
- Git only knows about the folder you are standing in.
- Amplify's GitHub connection is an app installation on the GitHub side, and the popup blocker is the usual reason it seems not to work.
- A static site needs no build command; Amplify just publishes the folder.
